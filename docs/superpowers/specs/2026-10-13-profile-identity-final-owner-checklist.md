### Physical freeze versus runtime activation

**Physical freeze gate:** F-E1–F-G2 are owner APPROVED; Account Verification must accept the four-table API's principal ownership, email revision, credential absence/CAS and transaction/error boundaries; physical review is documented in the [minimal addendum](../../database/vnext/identity-foundation/README.md). No table is formally frozen before relevant acceptance; migration allocation is an implementation prerequisite, not a table-shape decision.

**Runtime activation blockers only (under the recommended shape):** third-party mailbox OTP freshness, missing/unverified Google-email completion (no completed new User until valid proof), interactive reauth/recovery eligibility, OTP expiry/resend/abuse values, Argon2id library/cost benchmark, session protocol/lifetimes/revocation, mandatory security-audit sink, old-writer fencing and operator conflict remediation. These do **not** block authoring an independently reviewed additive empty schema. If a selected runtime design requires new durable state/columns, review that dependency before the affected schema freezes; do not invent it in the four-table slice. Audit/session-required mutations remain disabled until their transactional collaborator is accepted.
