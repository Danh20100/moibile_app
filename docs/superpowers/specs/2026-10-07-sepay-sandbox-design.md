## 1. Intent, authority and scope

Add `SEPAY` beside `MOMO` as a second optional current V1 provider. Preserve MoMo clients, records, signatures, result mapping, payment path and manual finance. SePay **Payment Gateway Sandbox**, one-time `PURCHASE` / `BANK_TRANSFER` / `VND`, supplies executable provider acceptance for this student project. SePay Bank Webhooks, Bank Hub, VA APIs, cards, recurring payments, production activation, refunds and void workflows are outside this change.

Authority remains Canonical v3.7 → ERD → frozen 29-table public catalog; technical gateway records remain outside `public`. Charge is receivable. Checkout is technical intent. Confirmed Payment, Payment Allocation, Payment Claim, Deposit application and Receipt remain separate. No callback or reconciliation automatically allocates a Payment, applies it to Deposit or issues Receipt. Manual cash/transfer remains operator-authorized and server-derived `USER_RECORDED`; clients cannot supply gateway provenance.

**Approval decisions, not existing authority:**

- Promote this specific second optional provider from general provider expansion FUTURE into current V1. Further provider/platform expansion and “gateway as MVP dependency” remain FUTURE.
- Preserve “verified payment-success IPN only” for **MoMo**. For **SePay**, authenticated IPN plus merchant REST read-back, or an explicitly authorized reconciliation using the same REST evidence validator, may settle. This is an explicit extension of the old IPN-only wording.
- Use executed SePay Sandbox evidence for the optional-provider sandbox acceptance requirement. Preserve MoMo UAT/signature incompatibility as `BLOCKED_EXTERNAL` / `UNVERIFIED`; SePay PASS must never be reported as MoMo PASS. Merge readiness and full V1 acceptance are separate assessments (§9); design approval does not automatically waive an external gate.
- Sandbox evidence represents provider-generated simulated transfers. Enable SePay only against isolated nonproduction application/finance data, never mixed with operational real-money records. Label the method “SePay Sandbox”. Production SePay is gated.

- [Order detail API](https://developer.sepay.vn/vi/cong-thanh-toan/API/don-hang/chi-tiet-don-hang): authenticated order details with transaction history; example statuses include CAPTURED, CANCELLED and AUTHENTICATION_NOT_NEEDED. Public docs parameter is provider `order_id`.
- Official SDK revision `62178220f36cda2f6657731ef182ecd84dd67e2f`: [checkout signer](https://github.com/sepayvn/sepay-pg-node/blob/62178220f36cda2f6657731ef182ecd84dd67e2f/src/checkout.ts) uses HMAC-SHA256/Base64 over comma-joined selected `key=value` fields **in insertion order**, not alphabetic order. `custom_data` is not in its signed allowlist; do not trust it for correlation. [Order client](https://github.com/sepayvn/sepay-pg-node/blob/62178220f36cda2f6657731ef182ecd84dd67e2f/src/order.ts) passes invoice number to the detail path, conflicting with public docs. [Client](https://github.com/sepayvn/sepay-pg-node/blob/62178220f36cda2f6657731ef182ecd84dd67e2f/src/client.ts) uses static environment URLs; do not import this shared mutable configuration into the app.

Task 0 pins these contracts from official documentation/source or written provider clarification: form ordering/escaping and invoice bounds; same-invoice replay/resume guarantees, including already-paid/late-paid orders; lookup identifier and exact/paginated invoice discovery; stable API/IPN transaction identity; BANK_TRANSFER amount/status semantics; IPN authentication, failure response/body and retry/timeout policy. No SePay merchant credentials/account/tunnel were exercised here. All live contract and Sandbox gates are `UNVERIFIED`. MoMo's missing create signature remains a separate blocker; no bypass.

## 4. Architecture and ownership

Alternatives: extending one large service with provider conditionals is initially smaller but mixes verification; a general payment framework/queue adds unnecessary scope. Select **two small adapters plus the existing coordinator and a shared settlement helper**.

| Boundary | Ownership |
| --- | --- |
| Gateway controller/service | Principal authorization; default provider; durable key/fingerprint/correlation; replay policy dispatch; safe checkout projection. |
| `MomoGatewayAdapter` | Wrap existing MoMo client, strict request/response/IPN HMAC, result mapping, snapshot and 31-day dispatch policy unchanged. |
| `SepayGatewayAdapter` | Sandbox-only immutable form preparation/signing, handoff capability, IPN secret authentication, merchant API read-back, narrow normalization and SePay replay policy. No import of MoMo verifier/classifier. |
| `GatewaySettlementService` | Only internally verified normalized evidence; lock/reread/check exact identity/amount; immutable terminal rules; Payment/link/authorized creator Notification transaction. Not an HTTP endpoint or untrusted DTO service. |
| Finance repository | Technical checkout persistence and database backstops; no domain policy changes. |
| Android | Explicit method selection, provider-scoped local pending input, safe browser handoff/return, authorized backend refresh. Never marks payment from return query. |

Provider model is `GatewayProvider = 'MOMO' | 'SEPAY'`. A small registry contains exactly these adapters. Snapshot DTO/storage types live in `src/persistence/ports/gateway-checkout.types.ts`, so persistence no longer imports a concrete HTTP client. Use a discriminated union by record provider; keep stored MoMo snapshot bytes/keys unchanged, including legacy null snapshots. SePay snapshot contains environment, merchant ID, fixed endpoint/API origin, operation/method/currency and fixed return URLs; immutable amount/invoice/description are also bound from row columns. No keys, signatures, Basic Auth, Google credentials or handoff tokens are stored.

Adapter interface: `prepareIntent(input, checkoutId): PreparedGatewayIntent`; `prepareHandoff(record): Promise<PreparedHandoff>`; `replayReason(record, now): string | undefined`; `authenticateNotification(input): void` before lookup; `verifyNotification(input, record): Promise<VerifiedGatewayEvidence>`. MoMo notification verifies locally; SePay performs REST read-back outside DB locks. SePay additionally supports `reconcile(record): Promise<VerifiedGatewayEvidence>`. Internal evidence includes provider/merchant scope, invoice, bound remote order ID, amount/currency, normalized outcome, stable settlement ID, stage and minimal redacted observations. Do not expose arbitrary client-created evidence to settlement.

## 5. API and backward compatibility

All paths below are under `/api/v1` unless stated otherwise.

| Endpoint | Contract |
| --- | --- |
| `POST /finance/checkouts` | Existing principal and UUID Idempotency-Key. Body `{tenancyId, amount, provider?: 'MOMO'|'SEPAY'}`; omission defaults **MOMO**, never config-dependent fallback. Explicit null/unknown provider rejected 400. After request validation and actor/resource authorization, lookup existing user/key and compare canonical provider/tenancy/amount fingerprint **before provider availability/config/snapshot creation**. A mismatch is always 409, even if the selected provider is disabled. A matching key returns its durable intent; availability only gates eligible new work/handoff. |
| `GET /finance/checkouts/:id` | Existing authorization/status shape; no provider create call or reconciliation. Provider returned from stored row. Preserve existing MoMo payUrl, replay flags and status semantics. |
| `POST /finance/checkouts/:id/reconcile` | New **SePay-only** operation, authenticated creator with current ACTIVE/ENDING write access, no evidence in body. Performs read-only provider query then local evidence/settlement; no remote create/cancel/refund. MoMo returns 422 and keeps its existing path. Rate-limit/coalesce per intent as an implementation safeguard. |
| `POST /finance/checkouts/:id/resume` | Explicit SePay recovery request by the authenticated creator/current writer. Read back the exact invoice, then return a resume handoff capability only under the verified same-invoice replay rule in §6; otherwise return durable unresolved state/recovery reason. Never reset the first claim or allocate another invoice. |
| `POST /finance/checkouts/momo/ipn` | Existing strict DTO/HMAC and 204 empty ACK unchanged. Explicitly require stored provider=MOMO. |
| `POST /finance/checkouts/sepay/ipn` | Public-to-identity endpoint with mandatory provider secret validation and typed nested shape. Unknown/unverified input never writes money. Commit or verified duplicate → raw 200 `{"success":true}`, without global envelope. All provider-facing failure codes/bodies follow Task 0's verified response matrix, not hard-coded 401/409/503 assumptions. If that matrix is unresolved, the IPN channel remains disabled. |
| `GET /finance/checkouts/sepay/handoff/:token` | Side-effect-free public HTTPS landing page: validate token and read eligibility through a read-only repository path, not a service that performs lease recovery; render an escaped same-origin POST dispatch button. No claim, lease/timestamp/state update, provider call or provider form/signature release. Prefetch, reload, link scanner and repeated GET change zero rows. |
| `POST /finance/checkouts/sepay/dispatch/:token` | Explicit user submission of that landing-page button. Verify capability/action/expected attempt and same-origin browser request, atomically claim dispatch, commit, then return the fixed-target signed provider form. No provider form is issued before this POST. Duplicate/concurrent POST for that attempt cannot issue a second form. |
| `GET /finance/checkouts/sepay/return/:result` | Fixed `success|error|cancel` allowlist; inert return page with “return to app” URI `trooi://payment/sepay`. Never reads query status as evidence or updates checkout. No arbitrary redirect target. |

Use the existing checkout response fields for compatibility. Add optional `environment: 'SANDBOX'` only to SePay projections. `payUrl` for SePay is the HTTPS **backend bridge**, not a fabricated provider GET URL; MoMo payUrl remains signed provider URL. No form fields/signature in Android API, no secret token in persistent session hints. Handoff URL is a temporary payment capability and must be redacted from logs and excluded from analytics.

Idempotency uniqueness remains `(createdByUserId,key)`, **not provider-scoped**: the same key changed to a different provider returns 409. Different method is a new explicit user intent/key, not automatic failover. Existing MoMo fingerprints remain exactly SHA256 of `['MOMO',tenancyId,amountVnd]`; no migration recalculation. Omitted provider and explicit MOMO are equivalent. Existing null-snapshot legacy records remain replay-blocked with the same IDs/payment links.

### Explicit origin topology

There are three distinct origins: (A) Android authenticated API origin from existing API-base configuration, optionally emulator `http://10.0.2.2:3000/api/v1` in backendDebug; (B) public HTTPS merchant application origin from backend `SEPAY_PUBLIC_BASE_URL`, exposing landing/dispatch/return/IPN via the same backend deployment and **same isolated database**; (C) SePay's fixed checkout/API origins. A public tunnel/reverse proxy may map B to A's backend; it must not point to another fixture server or dataset. Assert deployment/dataset identity before acceptance.

Android pins B separately with Gradle `trooiPaymentPublicOrigin` / env `TROOI_PAYMENT_PUBLIC_ORIGIN`, emitted as `BuildConfig.PAYMENT_PUBLIC_ORIGIN`. It must equal the origin of backend `SEPAY_PUBLIC_BASE_URL`; do not derive it from A, response `payUrl`, incoming Host or proxy headers. Missing/mismatched B blocks SePay browser launch only. Android authenticated create/read/reconcile/resume calls stay on A; Google bearer credentials never appear in browser URLs/forms. The browser uses B's capability routes, then POSTs to C. All provider return URLs/IPN target B, never emulator/private A. MoMo signed-provider URL validation remains separate and unchanged.

Keep whole integer VND `[1000,50000000]` as the initial **local checkout policy** for both providers, preserving existing UX; this is not asserted to be SePay's published limit. Require Sandbox support evidence before enabling. Decimal parsing remains exact before numeric conversion.

## 6. SePay lifecycle, failures and reconciliation

1. Validate request and authorize; lookup user/key and enforce fingerprint conflict before checking provider availability. Only a missing intent reaches new-provider config/snapshot preparation. Allocate immutable invoice `TROOI-SEPAY-<checkout UUID without dashes>` and local request correlation ID, not a claimed SePay idempotency parameter. Persist nonsecret snapshot/fingerprint and commit before returning any handoff.
2. Prepare a signed form locally; do not POST SePay from the checkout API. `CREATED` for SePay means **local handoff ready**, not provider order acceptance. MoMo CREATED continues to mean verified create acceptance. Neither means Payment. Return a fresh short-lived capability when eligible.
3. Landing GET reads only. User-initiated POST dispatch validates token/provider/expiry/config/action and expected attempt, then locks/rereads the row and revalidates its creator's current ACTIVE/ENDING tenancy write access inside the claim transaction. The capability delegates only this dispatch, not finance read access or another principal. Atomically advance `handoff_attempt`, set first `handoff_claimed_at` and `first_dispatch_at` once, and mark uncertainty; commit before releasing the provider form. Token binds expected attempt so concurrent/repeated POST can release at most one form per attempt. Browser explicitly submits that returned form to SePay. No DB lock spans browser/provider network.
4. A claim proves local intent to dispatch, **not browser delivery/submission**. A crash or closed browser after claim is indistinguishable from accepted-but-lost provider POST. Same-key checkout replay/read returns the original intent and `HANDOFF_RECONCILIATION_REQUIRED`, without a form. Expired unclaimed landing tokens renew through the same POST/key. Claimed recovery follows the rules below; no automatic external resubmission or new invoice.
5. On IPN, authenticate secret before reading/querying intent, locate by exact SEPAY/merchant/invoice namespace, validate typed identity/amount/currency/method, then query trusted merchant API outside a DB transaction. Bind remote order ID only from verified matching response. On API uncertainty or invalid evidence, keep money/state unchanged and use Task 0's verified failure response policy; do not assume 503 or acknowledge success just to stop retries.
6. Require order invoice, merchant credential scope, VND/exact amount, expected BANK_TRANSFER method and **one unambiguous APPROVED PAYMENT transaction** corroborated by provider API. `CAPTURED` without validated transaction is not sufficient. Stable API transaction ID and its confirmed IPN mapping form settlement identity. Missing/multiple/mismatched/partial/overpaid/unsupported evidence means reconciliation, no guessed Payment.
7. Settle through the shared helper. Verified success can settle INITIATED/CREATED/UNKNOWN, including IPN before return. A matching duplicate verifies the existing committed Payment/link and returns 200. Different successful transaction or contradictory terminal evidence is an internal conflict; provider-facing IPN response is pinned by Task 0, while authenticated application commands retain 409. Never second Payment or reversal. Logs contain only internal checkout ID, provider, normalized outcomes and stage.
8. Authorized reconciliation can recover a missed IPN using the same independently validated API order/transaction evidence. GET never performs this. Query 404/not-yet-visible remains UNKNOWN; pending AUTHENTICATION_NOT_NEEDED is nonterminal. Browser cancel/error is never FAILED. Verified CANCELLED remains unresolved/non-replayable until finality is explicitly established by contract gate; do not copy MoMo final-failure rules. Unsupported TRANSACTION_VOID after success is a recorded conflict requiring manual reconciliation, not automatic finance correction.

### Claimed-but-unsubmitted recovery without guessing

The UI describes “dispatch outcome unknown”, not “never submitted” based on client reports. `POST reconcile` queries the exact immutable invoice: verified paid evidence settles; a known pending order stays nonterminal and cannot cause a fresh order; 404/empty search/time passage proves neither absence nor non-submission and never clears claim. Timeout, cancelled browser and expired capability also do not clear claim or create a new key.

An explicit `POST resume` may issue a new **resume** capability for the same invoice/immutable fields only if Task 0 establishes a provider guarantee that replaying that invoice resumes/rejects the existing order and cannot create another order/charge, including races with late success. A lookup result alone is insufficient. Reconcile first; paid returns the original settled checkout, conflicting/ambiguous evidence blocks resume. POST dispatch rechecks terminal state and atomically advances the expected attempt; first-claim timestamps/IDs remain immutable. A further response loss repeats this explicit recovery protocol, never auto retries. This supports the genuinely unsubmitted case without asserting it can be recognized locally.

If that replay guarantee is unverified/unsupported, return `PROVIDER_RESUME_CONTRACT_REQUIRED` and keep the correlated intent visible for provider-supported reconciliation/redelivery. The optional SePay channel cannot claim recoverable-checkout acceptance or be enabled for general use until that path is proven; no reset-claim, random new invoice, blind retry or simulated absence workaround is permitted. A future provider-supported terminal cancellation/new-intent policy needs separate evidence/approval and is not silently implemented here.

Handoff defaults: 5-minute token lifetime; purpose/provider/checkout/action/expected-attempt/expiry bound with independent HMAC-SHA256 key, timing-safe verification. Landing CSP permits only same-origin dispatch; returned provider form CSP permits only fixed SePay Sandbox. Both use `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, escaped attributes, fixed targets and no third-party scripts/credentials. Landing uses an explicit POST button; dispatch response uses a visible provider-submit button. No reusable tokens in Android storage. API timeout default5s; IPN budget default10s is subordinate to Task0 verified timeout/retry rules, not a claim about provider contract.

API callbacks and explicit reconciliation use fresh server evidence; timestamps alone do not reject legitimate delayed delivery. No invented freshness window, retention period or provider retry count. Coalescing is only an optimization: PostgreSQL locks/uniqueness prove at-most-once writes. External transport never runs while holding the checkout lock. Reconciliation snapshots are rechecked under lock so a concurrent terminal outcome wins safely.

## 7. Safe forward migration

Create `000005_optional_sepay_gateway` (TS runner + up/down SQL); never edit 000003/000004. Current catalog contains migrations through 000004. Recheck deployed/head state at execution; choose the next unused forward number if that changes.

- Expand `ck_gateway_checkouts_provider` to MOMO/SEPAY. Retain all public tables, FKs, client key/result-link uniqueness and immutable intent trigger.
- Make snapshot validation provider-conditional: preserve **exact** MoMo seven-field/autoCapture/partner checks, legacy null handling and numeric transId rule; strict SePay key/type allowlist, Sandbox endpoints/environment/merchant binding and nonempty bounded opaque transaction ID. A SePay-shaped snapshot cannot pass as MoMo, or vice versa. Existing stronger whole-VND bounds remain.
- Add `provider_remote_order_id text NULL`, `handoff_claimed_at timestamptz NULL`, `handoff_attempt integer NOT NULL DEFAULT 0`; remote ID/first claim bind once and never change/reset; attempt advances atomically and never decreases. No rewrite of existing MoMo identities/snapshots/fingerprints; the new attempt counter is unused for MoMo. SePay merchant scope is `sandbox:<merchantId>`; MoMo partner values stay verbatim.

- Invoice lookup uses `(provider,merchantScope,provider_order_id)`; remote lookup uses `(provider,merchantScope,provider_remote_order_id)` and never falls back to invoice lookup or assumes equality. Preserve the old global `provider_order_id` unique guard as well as scoped guards: equal local invoice strings across merchants/providers still collide and are rejected, not silently rerouted. Generate a SEPAY namespace prefix for new invoices; if it collides with an old MoMo value, initial insert rolls back before any handoff, retry local UUID allocation only for a new not-yet-persisted intent. Existing-key replay never changes invoice. Equal remote IDs across different provider/merchant scopes are allowed; equal remote ID within one scope is a conflict. Invoice and remote IDs may have the same string because their roles/indexes are distinct. MoMo remote ID stays NULL.
- Preserve provider/merchant/transaction and resultingPayment uniqueness. Add scoped remote-order uniqueness. SePay transaction IDs are validated opaque strings, not MoMo numbers. Keep numeric `provider_result_code` for MoMo; SePay status lives in normalized outcome/redacted evidence with numeric code NULL. Extend stage check with `RECONCILIATION` while retaining existing values.
- Move the 31-day predicate from global lease SQL to provider-conditional SQL/policy; retain it exactly for MoMo. SePay does not call acquire-dispatch lease for form creation; one-time browser claim is its external-attempt backstop.
- No row rewrite, snapshot reconstruction, secret persistence or fingerprint change. Upgrade/repeat migration must preserve legacy, active and settled MoMo identities and linked Payment byte-for-byte.
- Deploy schema before new backend; keep SePay disabled until backend/Android/contract gates are ready. Old backend remains compatible with MoMo rows but must not receive SePay traffic during a rollback. Down migration refuses if any SEPAY row exists; never delete such records to make rollback pass. No production rollback of paid/unresolved data.
